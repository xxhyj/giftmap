# Giftmap (선물지도)

"누구에게 무엇을 선물해야 할지 모르겠다"는 순간에, 관계·상황·예산을 몇 번 고르면
어울리는 **실제 판매 상품**을 골라주는 안드로이드 앱.

판매처 세 곳(텐바이텐·알라딘·무신사)의 공개 상품 페이지에서 모은 **1,814개 상품**을
21개 분류로 다루고, 추천은 서버에서 OpenAI가 후보 중에서만 고른다.

```
Android 앱  ──►  Vercel API  ──►  Supabase (상품 DB)
(주소 하나만 내장)   (키 보관)    └►  OpenAI   (추천)
                     ▲
                  crawler/  Playwright 수집기 (오프라인, 앱과 분리)
```

> **비상업적 포트폴리오 프로젝트다.** 판매처와 제휴 관계가 없고 결제·중개를 하지 않는다.
> 상품 정보는 공개 페이지에서 읽은 수집 시점의 값이며, 구매는 판매처 페이지에서 이뤄진다.
> 자세한 기준은 [데이터 출처와 경계](#데이터-출처와-경계)에 적었다.

## 만들면서 내린 판단

기능 목록보다 이 부분이 이 저장소의 내용에 가깝다.
각 항목은 **부딪힌 문제 → 고른 방법 → 그 이유** 순이다.

### 앱에 키를 넣지 않으려고 서버를 뒀다

처음에는 앱이 Supabase에 직접 붙었다. 읽기 전용 키라도 APK를 뜯으면 나오고, OpenAI를 쓰려면
그 키까지 앱에 들어가야 했다. `server/`(Vercel Functions)를 두고 앱에는 `API_BASE_URL` 하나만
남겼다. Supabase service_role 키와 OpenAI 키는 Vercel 환경변수에만 있다.

되돌릴 수 있도록 한동안 두 경로를 나란히 두고 `USE_MOCK`으로 갈랐다가, 실기기 검증이 끝난 뒤
예전 경로를 지웠다.

### 모델이 상품을 지어내지 못하게 만들었다

LLM에게 "선물을 추천해 줘"라고 하면 없는 상품과 그럴듯한 링크를 만들어 낸다.
그래서 모델에게는 **고르는 일만** 준다.

1. 서버가 조건에 맞는 실제 상품 후보 24개를 DB에서 추린다
2. 모델은 그 목록 안의 id만 고를 수 있다
3. 앱은 받은 id를 자기 카탈로그에서 다시 확인하고, 없으면 서버에 그 상품 하나를 되묻는다
4. 서버도 모르는 id는 버린다

결과가 3개 미만이면 서버가 `fallback: true`를 돌려주고, 앱은 **로컬 결정론 엔진**으로 추천을
이어간다. 서버가 죽어도 추천 화면이 비지 않는다.

### 도서가 홈을 뒤덮는 문제 — 한도와 그 한도의 한계

알라딘을 붙이자 홈이 책으로 뒤덮였다. 원인은 셋이었다.

- **분류 오류**: 알라딘 상품 327개 중 도서로 분류된 것이 2개뿐이었다. "Student Book" 같은
  상품명 키워드 때문에 책이 문구·취미로 샜다 → 공급원이 분류를 마지막에 판단하는 훅을 뒀다
- **페이지네이션**: `order()`에 `ascending`을 적지 않아 내림차순으로 받고 있었고,
  `sort_order`가 전 행에서 같아 첫 페이지가 한 공급원으로만 채워졌다 → 정렬을 고정하고
  공급원 안의 순번을 매겨 페이지마다 공급원이 섞이게 했다
- **노출 편중**: 홈의 여섯 줄이 각자 상품을 뽑아 같은 상품이 여러 줄에 나왔다 →
  줄들을 한 번에 만들고 장부 하나를 공유한다

노출 한도는 "도서 15%, 한 판매처 35%"인데, **판매처가 셋이고 그중 하나가 책만 팔면 두 한도를
동시에 만족하는 배치가 존재하지 않는다**(15% + 35% + 35% < 100%). 그래서 목록이 실제로 가진
다양성만큼만 한도를 풀어 준다. 지킬 수 없는 약속을 지키려다 홈이 비는 쪽이 더 나쁘다.

### 인앱 브라우저: 로그인을 강요하지 않는 CTA

상품 상세의 "상품 보러 가기"는 판매처 **앱**이 아니라 웹 페이지를 Giftmap 안에서 연다.
판매처 앱은 대개 로그인부터 요구해서, 그냥 상품을 보려던 사람에게는 막다른 길이 된다.
웹 페이지는 로그인 없이 보이고, 구매까지 갈 사람은 그 페이지에서 스스로 앱을 고를 수 있다.

알라딘이 모바일 주소로 보낼 때 `http`로 내려보내 Android 9+의 평문 차단에 걸린 적이 있다
(`ERR_CLEARTEXT_NOT_PERMITTED`). 평문 주소는 https로 올려 다시 연다.

### 첫 화면이 멈추던 문제

상품이 1,800개가 되자 앱을 켤 때 전부 받아 그리느라 화면이 멈췄다(ANR). 첫 화면에 필요한
120개만 먼저 받고 목록 끝에서 이어 받는다. 서버가 같은 상품을 다시 보내도 목록에 두 번 붙지
않도록 받은 id를 기억한다.

### 기다리는 시간 21초 → 7초

추천 한 번에 21~25초가 걸렸다. 후보 40개를 태그·상황·관계 배열까지 붙여 보내느라 프롬프트가
컸다. 후보는 이미 조건으로 걸러 뽑은 것이라 그 정보를 다시 보낼 이유가 없어서 id·이름·브랜드·
가격·분류만 남기고 24개로 줄였고, 고르기만 하는 일이라 `reasoning_effort`를 낮췄다.

그 과정에서 앱이 20초에 포기하고 있던 것도 드러났다. 서버는 45초까지 기다리는데 앱이 먼저
끊어, 서버가 잘 고르고 있어도 매번 로컬 엔진으로 떨어졌다.

### 실패를 데모로 덮지 않는다

실제 상품 모드에서 읽기에 실패하면 번들 데모 상품으로 채우지 않고 **오류·재시도 화면**을 띄운다.
데모가 섞이면 "상품 보러 가기"가 동작하지 않는 상품이 화면에 생긴다. 조용히 잘못된 것을
보여 주는 것보다 안 되는 것을 알리는 편이 낫다.

다만 순간적인 상류 장애까지 오류 화면이 되지는 않게, 읽기는 서버에서 한 번 다시 시도한다.
Supabase 무료 플랜이 쉬다 깨어날 때 첫 질의가 9초 넘게 걸리는 것을 로그로 확인하고
타임아웃을 그에 맞췄다.

## 구조

```
lib/                 Flutter 앱 (Dart 87개 파일)
├── app/             MaterialApp, AppScope(의존성 주입), AppShell(바텀 탭), AppRouter
├── core/            테마, 공통 위젯, 설정(ApiConfig/ApiBootstrap), HTTP 클라이언트
├── data/            번들 JSON: 카테고리 / 위험 규칙 / 검색어 템플릿 / 데모 상품
└── features/        feature-first: home, categories, search, products,
                     library(찜), gift_finder, history, anniversary, settings, splash

server/              Vercel Functions (JS 18개 파일, 외부 의존성 0개)
├── api/             health, products, products/[id], recommend, search-events
└── lib/             env, http, validate, supabase, products, recommend, ratelimit

crawler/             Playwright 수집기 (JS 15개 파일, 앱이 호출하지 않는 오프라인 도구)
└── src/adapters/    공급원별 어댑터 (텐바이텐·알라딘·무신사)

supabase/migrations/ 스키마
```

- 의존 방향은 `presentation → application → domain`, `data`는 domain 계약을 구현한다
- 상태 관리는 `ChangeNotifier` + `InheritedWidget`만 쓴다(상태관리 패키지 없음)
- 라우팅은 `Navigator` + `MaterialPageRoute`(라우팅 패키지 없음)
- 추천 점수 계산은 엔진 두 개에만 있고 화면은 계산하지 않는다

자세한 설계는 [docs/ARCHITECTURE.md](docs/ARCHITECTURE.md), 작업 기준은
[CLAUDE.md](CLAUDE.md)에 있다.

## API

| 메서드 | 경로 | 하는 일 |
| --- | --- | --- |
| GET | `/api/health` | 살아 있는지와 환경변수가 채워졌는지(값은 담지 않는다) |
| GET | `/api/products?page=&limit=&category=&query=` | 상품 한 페이지 |
| GET | `/api/products/:id` | 상품 하나 |
| POST | `/api/recommend` | 조건에 맞는 실제 상품 3~5개 |
| POST · GET | `/api/search-events` | 익명 검색 기록 / 집계 |

오류는 어디서 나든 모양이 같다. 입력은 모두 검증하고(모르는 값은 버리고, 검색어에서 PostgREST
필터 문법을 뜻하는 문자를 지운다), 모델 호출은 IP 기준으로 분당 횟수를 제한한다.

## 추천 엔진 (로컬 폴백)

서버 추천이 실패했을 때 쓰는 결정론적 엔진이다. **같은 입력은 항상 같은 결과**를 만든다
(동점은 상품 id 오름차순).

```
base                 30
occasion match     0..25      budget fit        0..25
recipient match    0..20      preference match  0..10
age match          0..5       direction bonus   0..12
stale penalty        -8       risk penalty     0..-50
avoidTags 충돌 / riskLevel == avoid → 제외
```

카테고리 방향(`LocalRecommendationEngine`)을 먼저 정하고, 그 방향을 보너스로 반영해 상품을
점수화한다(`ProductRecommendationEngine`). 같은 분류·브랜드가 앞자리를 채우지 않게 벌려 놓는다.

## 검증

```bash
dart format --output=none --set-exit-if-changed lib test
flutter analyze          # 0 issues
flutter test             # 273 passed
npm --prefix server test # 63 passed
```

서버 테스트는 계정도 키도 배포도 없이 돈다. 가짜 요청·응답으로 핸들러를 직접 부르고,
응답에 키가 섞여 나가지 않는지도 확인한다.

자동 테스트로 잡히지 않는 것(첫 로딩 시간, 이미지, 인앱 브라우저 복귀, 추천 흐름)은
실기기에서 `adb`로 확인했다. 이 저장소의 버그 대부분은 실기기에서 나왔다.

## 실행

```bash
flutter pub get
flutter run                     # 번들 데모 상품 46종으로 동작(설정 불필요)

# 실제 상품(배포된 API 사용)
flutter build apk --release \
  --dart-define=USE_MOCK=false \
  --dart-define=API_BASE_URL=https://giftmapapi.vercel.app
```

앱에 들어가는 값은 `API_BASE_URL` 하나다. 값을 주지 않으면 번들 데모 데이터로 동작하며,
테스트도 이 경로를 쓴다.

서버는 GitHub `main`에 푸시하면 Vercel이 `server/`를 자동 배포한다
([server/README.md](server/README.md)). 수집기 실행법은 [crawler/README.md](crawler/README.md).

## 데이터 출처와 경계

- **공개된 상품 페이지만 읽는다.** `robots.txt`가 허용한 경로만 방문하고,
  로그인·CAPTCHA·접근 제한은 우회하지 않는다. `robots.txt`를 받을 수 없으면 수집하지 않는다
  (네이버쇼핑은 `Disallow: /`, 쿠팡은 robots.txt 자체가 403이라 대상에서 제외했다)
- **값을 지어내지 않는다.** `schema.org/Product` JSON-LD를 우선 쓰고, 없으면 공개 메타데이터를,
  그래도 비면 화면의 공개 표시값을 읽는다. 가격 근거가 없으면 `null`로 두고 화면에는
  "가격 확인 필요"로 표시한다. 0원으로 적지 않는다
- **가격과 재고는 수집 시점의 스냅샷**이다. 실시간이 아니며 판매처와 다를 수 있다는 고지를
  상세 화면에 붙인다. 품절은 공급원이 알려 줄 때만 표시하고, 모르면 품절로 단정하지 않는다
- **제휴·중개·결제가 없다.** 구매는 판매처 페이지에서 이뤄지고 Giftmap은 관여하지 않는다.
  제휴 링크나 수수료 구조가 없다
- **검색어는 익명으로만 남긴다.** 사용자 id·기기 id를 보내지 않고, 20자를 넘거나 문장처럼 긴
  입력은 개인적인 내용을 담을 수 있어 아예 기록하지 않는다. 집계는 3회 이상 검색어만 센다
- 번들 데모 상품 46종은 실제 브랜드·상품이 아니며 DEMO 배지와 고지가 붙는다

실제 서비스로 운영하려면 각 판매처와의 제휴가 필요하고, 이 프로젝트는 그 단계에 있지 않다.

## 한계

솔직하게 적어 둔다.

- **판매처가 셋뿐이다.** 다이소는 이번 범위에서 제외했고, 대형 오픈마켓 두 곳은 위 기준 때문에
  대상이 아니다
- **상품이 늙는다.** 수집기를 주기적으로 돌리는 구조가 없어 지금은 손으로 실행한다
- **추천 기록과 기념일은 메모리에만 있다.** 앱을 다시 켜면 비워진다
  (찜과 최근 본 상품은 기기에 저장된다)
- **로그인·결제·장바구니가 없다.** 결제를 앱에서 하지 않기로 한 설계라 의도한 제외다
- APK가 디버그 키로 서명돼 있어 스토어에 올릴 수 없다
